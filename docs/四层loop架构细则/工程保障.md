## 二、检查点原子性（防损坏）

- 写 checkpoint.json 用 **write-temp + atomic-rename**：先写 `.tmp` → fsync → `os.replace()` 原子替换
- 含 `schema_version` 字段（当前 1），格式升级时做迁移
- 启动时校验完整性（JSON schema 校验），损坏回退 `.bak`（滚动保留 3 份）
- **保存粒度**：每个候选处理完即保存（批内中断不丢进度）

## 三、run.lock 并发锁（防并发 + 防僵尸）

- 内容 `{pid, start_time, ttl: 3600}`（1 小时超时）
- **僵尸锁判定**：start_time 超 TTL 或 pid 进程不存在（tasklist 检查）→ 强制接管
- 正常退出（含异常 finally）必须删锁
- 锁占用时新事件进 pending_events.json 排队
- 回测任务严格串行（防互相覆盖 backtest_history.csv 与权重状态）
- cron 拉起先查锁：存在且未超时 → 本次跳过

## 四、事件总线（防死锁/活锁，反向触发）

|事件|触发动作|
|---|---|
|factor_rolled_back（L4回滚）|L3 补位评估（挑下一未测候选）|
|batch_completed（L2批完成）|候选池 ≥3 → L3|
|regime_changed（市场切换）|L4 对"观察中"因子复核|
|data_ready（数据就绪）|L3 例行回测|

- 事件表写 events.log（时间戳 + 事件 + 动作 + 结果）
- 暂停状态（如连续 3 次无改进）不代表永久停止：任何上层事件都会重新评估暂停条件

## 五、灾难恢复（数据健康门禁）

- 启动先扫描 `D:\quant_data\`：日期连续性（factor_daily_incr 缺失天数）+ 关键字段非空率（收盘/ret_1d/成交量）
- 缺失日期 >5% 或非空率 <95% → **暂停 loop + 告警**，不自动跳过、不自动重拉（等人工确认数据源）
- 扫描结果写 data_health.json；通过才允许 L1-L4 任何动作

> L1/L2/L3 的新增字段随各层 🔧P1/P2 项落地；字段定义以对应分层文档为准，本表只列落盘位置与范围。

**健康度 dashboard**：每次 loop 结束刷新 dashboard.json；池健康分 = f(启用数, 平均ICIR衰减, 池内平均相关性, 实盘偏差均值)（0-100）；**<60 → 触发全量体检**（重跑所有启用因子 L2 检验），趋势（近5次）供人工判断。

**门禁有效性自检（🔧P1，新增）**：每次 loop 结束统计各层每一关的通过率与指标非空率，出现以下任一情况即告警——

- 某关通过率恒为 **100%**（累计 ≥20 次判定仍从未拒绝过任何候选）
- 某关的指标恒为空 / 恒为默认值（如 regime 恒为 `{}`、半衰期恒为 12 月）
- 某关的异常兜底触发率 > 10%（`except → return True` 这类保守放行路径）

**动因**：`l2_regime` 因 `_cand` 列从未物化，长期抛异常并走 `except: return True, {}` 分支，**这一关从未拒绝过任何因子而日志毫无异常**（见 L2 第九章缺陷 1）。"假门禁"比没有门禁更危险——没有门禁至少不会给出虚假的安全感。任何带 `except → 放行` 兜底的检验都必须落盘兜底触发次数。

**成本追踪**：按 layer 记 token 消耗与成本；单因子平均成本 = 总成本/入库因子数；上升趋势明显 → 提示 prompt 效率下降，需调整生成策略。
